# Прототип експорту конструктора 1d20 → Foundry

Імпортер обробляє персонажів за правилами **2014 і 2024, рівні 1–20, включно з мультикласом**, через конвертери Plutonium: **Foundry 13 / dnd5e 5.3.x** або **Foundry 14 / dnd5e 6.x**. Обмеження на конкретний клас, расу чи передісторію немає. Звичайний JSON-експорт Roll20 для цього не використовується. Живий імпорт користувач підтвердив на Foundry 14; для Foundry 13 перевірено схеми, API, каталоги та автономні тести, але живий імпорт ще не підтверджено.

Після оновлення виконайте нову консольну команду на сайті та скопіюйте новий JSON: експортер **0.2.0** додає повніші володіння, джерела заклять і вибори класових здібностей. Формат залишається `schemaVersion: 1`; старі експорти читаються, але можуть потребувати додаткового вибору або повторного експорту.

## Команда для консолі

1. Відкрийте свого персонажа на <https://1d20.com.ua/character-builder/>. Дочекайтеся завантаження та завершення поточного вибору.
2. Відкрийте F12 → Console саме на вкладці конструктора.
3. Вставте **весь вміст** [`tools/character-builder-console.js`](../tools/character-builder-console.js) та натисніть Enter. Це одна самодостатня команда, без завантаження стороннього коду чи серверних запитів.
4. Команда поверне JSON, збереже його у `window.d20FoundryJSON` і спробує скопіювати в буфер. Якщо буфер недоступний, JSON усе одно залишиться у змінній.

Повторне копіювання вже отриманого знімка:

```js
copy(window.d20FoundryJSON)
```

Новий знімок після змін персонажа, поки сторінку не перезавантажено:

```js
copy(D20FoundryExporter.toJSON())
```

Зберегти JSON у файл:

```js
D20FoundryExporter.download()
```

Менший файл без портрета:

```js
copy(D20FoundryExporter.toJSON({includePortrait: false}))
```

Команда читає лише поточного героя (`dnd_character_v2`) і завантажений довідник. Вона не читає cookies, токени чи інших збережених героїв, не записує localStorage та не змінює персонажа. Ім'я, біографія, портрет, ігрові нотатки та інші поля поточного героя входять у знімок. Чернетки теж експортуються; незавершені кроки позначаються в `diagnostics`.

## Перевірка у Foundry

У світі має бути активний саме модуль **1d20.com.ua — Український переклад для Plutonium** (`1d20-ua-plutonium`), а також Plutonium. Налаштування «Вставляти посилання для імпорту» має бути увімкнене. Після оновлення файлів перезавантажте клієнт Foundry.

Скопіюйте JSON та натисніть **Ctrl+V над аркушем персонажа або бічною панеллю**, поза текстовим полем — так само, як для посилань на предмети. Один обробник розпізнає JSON персонажа або посилання. Для JSON одразу починається підготовка; вкладені в нього посилання не імпортуються як окремі предмети. Окремої кнопки запуску у Foundry немає.

Після підготовки з'являється звіт із кількостями сутностей, уточненнями та дією «Заповнити аркуш» або «Створити персонажа». Власний порожній аркуш під курсором без предметів та ефектів стає ціллю заповнення; його характеристики, гроші й біографія замінюються. В інших випадках пропонується створення нового персонажа, що потребує дозволу Foundry на створення Actor. Наявний заповнений персонаж не перезаписується. Скасування звіту нічого не записує.

Імпортер збирає всі класи з їхніми рівнями, підкласи, расу / підрасу, передісторію, класові й расові здібності, вибрані опції здібностей, риси та спорядження конвертерами Plutonium. Володіння, експертиза, мови, інструменти, майстерність зброї, гроші, характеристики й ряткидки беруться зі знімка. Невибрані варіанти стартового спорядження не додаються. Кількості наборів враховуються: два набори по 20 стріл дають 40 стріл. Власні предмети без запису довідника стають предметами типу loot.

Класові закляття, закляття підкласу, раси, рис і містичні аркануми обробляються за джерелами отримання. Одне закляття від двох класів може мати дві копії з різними характеристиками. Зберігаються підготовленість, звичайні та pact-комірки, ліміти й відновлення застосувань із метаданих Plutonium. Якщо конструктор не передав характеристику расової чи іншої магії, імпортер запитає її один раз для цього джерела.

Спочатку створюється документ у пам'яті та звіряються HP, характеристики, КО, швидкість і володіння навичками. HP зберігають класовий advancement і хронологічний порядок рівнів мультикласу. Бонуси не додаються повторно, якщо Plutonium вже врахував їх. Необхідні поправки HP або перевизначення КО відображаються у звіті. Невиправлена розбіжність або відсутня сутність зупиняє імпорт до запису. Підготовлений персонаж записується одним створенням або штатним JSON-імпортом Foundry. Зміна аркуша іншим клієнтом під час підготовки також зупиняє імпорт.

Переносяться портрет, біографія, нотатки, поточні й тимчасові HP. Обладунки та щит обираються за спорядженням конструктора; явний стан equipped має пріоритет. Вихідні вибори залишаються у `flags.1d20-ua-plutonium.characterImport.selections`.

«Свої ресурси класу» (`state.resources`) стають окремими здібностями типу feat. Наприклад, «зяблики — 44» дає 44/44 використань і дію «Витратити 1», що витрачає ресурс цієї здібності. Число трактуємо як повний запас; конструктор не задає окремі поточний і максимальний запаси. Автоматичне відновлення не додається, його можна налаштувати у Foundry. Порожні рядки пропускаються. Текстове значення зберігається в описі без лічильника, із зауваженням у звіті. Автоматичні ресурси класів із довідника при цьому не дублюються.

Обмеження: вибори advancements для подальшого підвищення рівня ще потребують перевірки. Витрачені комірки конструктора збережені у вихідних виборах, але не відновлюються як витрачені ресурси Foundry. Безкоштовне расове/інше застосування налаштовується окремим лімітом; якщо опис також дозволяє витратити звичайну комірку, цей спосіб накладання треба перевірити в дії закляття. Умовні ефекти вибору раси та повна автоматизація правил залежать від даних Plutonium і модулів світу. Невідомий homebrew не замінюється схожою офіційною сутністю: потрібні відповідні дані у Plutonium.

Для роботи через консоль Foundry:

```js
// json — рядок експорту, який ви вже передали в цю вкладку.
const builder = game.modules.get('1d20-ua-plutonium').api.builder;
builder.inspect(json);        // Об'єкт короткого звіту без зміни Actor.
await builder.preview(json);  // Підготовка й діалог запису, як Ctrl+V.
builder.issues(json);         // Помилки / відсутні обов'язкові дані.
await builder.prepare(json);  // Дані Actor та перевірка без запису у світ.
// Якщо потрібного вибору характеристики магії немає, prepare завершується
// помилкою; Ctrl+V натомість відкриває діалог вибору.
// Власна інтеграція може явно вимкнути фінальний діалог:
// await builder.import(json, {actor: game.actors.get('ACTOR_ID'), review: false});
// await builder.import(json, {review: false}); // Створення нового.
```

Змінна `window.d20FoundryJSON` належить вкладці сайту і сама не переходить у Foundry. Передайте її вміст через буфер обміну.

### Виправлення старого імпорту з DEX у всіх навичок

Оновлений імпортер явно передає характеристику кожної навички (`skillRows.stat`), перевіряє її після підготовки й повідомляє про розбіжності підсумкових бонусів. Попередня версія пропускала характеристику; dnd5e 6 підставляла DEX для всіх переданих записів.

Щоб виправити вже імпортованого персонажа, перезавантажте клієнт Foundry, відкрийте лише його аркуш (або виділіть його токен) та виконайте в консолі Foundry:

```js
await game.modules.get('1d20-ua-plutonium').api.builder.repairSkills();
```

Команда виправляє лише характеристики навичок власного персонажа з маркером імпорту та точною ознакою старої помилки: усі 18 навичок мають DEX. Предмети, володіння, експертиза й додаткові бонуси залишаються на місці. За неоднозначного вибору команда зупиняється; конкретного Actor також можна передати аргументом. Повторно експортувати JSON для цього виправлення не потрібно.

## Адміністратору: готова кнопка

Для передачі розробнику сайту є [окрема інструкція з готовим сніпетом, підтримкою перерендеру й ручного копіювання](website-integration.uk.md).

Потрібен **один файл** [`tools/character-builder-export.js`](../tools/character-builder-export.js). Розмістіть його серед ресурсів сайту й підключіть після скриптів конструктора. Це наш адаптер, він викликає наявні `CBD` / `CBSheet`; копіювати код конструктора в модуль не потрібно. Додатковий endpoint, авторизація або налаштування CORS не потрібні.

Наприклад, у шаблоні після підключення скриптів конструктора:

```html
<script src="/assets/character-builder-export.js"></script>
<button type="button" id="copy-foundry-character">Копіювати для Foundry</button>
<span id="foundry-export-status" role="status"></span>
<script>
document.getElementById('copy-foundry-character').addEventListener('click', async () => {
    const status = document.getElementById('foundry-export-status');
    try {
        await window.D20FoundryExporter.copy();
        status.textContent = 'Дані персонажа скопійовано';
    } catch (error) {
        status.textContent = 'Не вдалося скопіювати: ' + error.message;
    }
});
</script>
```

Шлях `/assets/character-builder-export.js` у прикладі замініть на фактичний. Для динамічного інтерфейсу кнопку слід додати в шаблон підсумку й приєднати обробник там, де конструктор обробляє решту кнопок; інакше перерендер може видалити її.

Якщо обробник має доступ до живого об'єкта стану, передавайте його напряму. Це надійніше за читання збереженої копії:

```js
// currentCharacterState — поточний стан конструктора у вашому коді.
const payload = window.D20FoundryExporter.exportCharacter({state: currentCharacterState});
await navigator.clipboard.writeText(JSON.stringify(payload, null, 2));
```

`exportCharacter()` повертає звичайний JSON-сумісний об'єкт синхронно, `toJSON()` — рядок, `copy()` — Promise із скопійованим рядком. Розрахунки виконуються на копії стану. Кнопка та консоль використовують той самий адаптер і формат.

## Контракт v1

| Поле | Призначення |
|---|---|
| `format: "1d20.character"` | Маркер для розпізнавання у Foundry |
| `schemaVersion: 1` | Версія контракту; несумісна зміна потребує нової версії |
| `exporter`, `exportedAt`, `builder` | Версія адаптера, час експорту, версія конструктора та ідентифікатор його каталогу |
| `rules` | Система `dnd5e`, редакція 2014/2024 і правила homebrew зі стану |
| `character` | Ім'я, ID, сумарний рівень, список класів з рівнями й підкласами, раса та передісторія |
| `state` | Вихідний збережений/переданий стан **без втрати невідомих полів**: усі вибори, заклинання, спорядження, поточні HP, нотатки тощо, якщо вони є у стані |
| `snapshot.abilities` | `base` — вихідні характеристики; `final` — значення після бонусів |
| `snapshot.resolvedState` | Робоча копія з підставленими визначеннями раси/класу/передісторії, розрахованими підвищеннями та знімком для друку |
| `snapshot.mechanics` | Мови, інструменти, володіння зброєю й обладунками, бонуси HP, правила КО, перевірок і атак, вибір походження раси |
| `snapshot.casting` | Окремо для кожного класу: вибрані закляття, магія підкласу/рас/рис, аркануми, характеристика магії, класові опції й варіанти здібностей |
| Інші поля `snapshot` | Показники аркуша, володіння, експертиза, порядок класових рівнів, HP по рівнях, ресурси заклять та дані магії окремо для кожного класу |
| `references.entities` | Визначення сутностей, на які посилається стан/знімок, та їхні транзитивні залежності |
| `references.lookups` | Словники мов, інструментів і майстерності зброї |
| `diagnostics` | Незавершені кроки, невідомі ідентифікатори та недоступні розрахунки |

У записів довідника є `type`, `slug`, `nameEn`, `source`, `uid`, `parent`, `data`. `uid` — допоміжний ключ назви й джерела/ключ каталогу, **не готовий hash Plutonium**; для підкласів і підрас потрібно також враховувати `parent`. Якщо джерела немає в каталозі, `source` залишається `null`: імпортер має знайти сутність за точним slug у своїх даних. Не можна вибирати книгу за перекладеною назвою або підставляти PHB за замовчуванням.

`references.entities` **не є списком для масового імпорту**: там також можуть бути варіанти стартового спорядження та інші залежності визначень. Конкретний вибір береться зі `state` та відповідних полів `snapshot`. Custom-предмет без ідентифікатора зберігається у `state.equipment`.

Це формат передачі даних, а не Foundry Actor JSON. Класи, риси, заклинання, advancements та effects має створювати адаптер Plutonium. Фінальні характеристики призначені також для звірки: їх не слід записувати як базові перед повторним застосуванням бонусів. Нуль попереджень означає успішне зчитування, а не гарантію повного імпорту механік.

## Підтримка і перевірка

Експортер використовує внутрішній API поточної версії конструктора. Якщо функція зникне або зламається, її результат буде `null`, а причина потрапить у `diagnostics.warnings`; вихідний стан залишиться у файлі. Якщо відсутній сам стан або каталог, експорт завершується помилкою. Після змін API сайту адаптер потрібно перевірити.

```sh
node tools/build-character-builder-console.mjs
node --test tests/*.test.mjs
node tools/check-character-builder-export.mjs
node tools/check-character-import.mjs ../plutonium
```

Перший виклик генерує самодостатню консольну команду. Другий перевіряє експорт, Ctrl+V, мультиклас, HP, закляття й ресурси, вибір спорядження, скасування та запис лише після підготовки. Конвертери Plutonium і обчислення Actor у цих тестах замінені тестовими адаптерами: це не перевірка живого аркуша. Третій виклик перевіряє приклади 2014, 2024 та мультиклас на публічних скриптах сайту в ізольованому JavaScript-контексті.

Четвертий виклик звіряє експорти з установленим каталогом Plutonium. На поточних даних перевірено 108 згенерованих збірок: 27 класів на рівнях 1, 5, 11 і 20, 1220 виборів заклять, ідентичності 161 раси, 97 підрас, 171 передісторії й 330 підкласів, а також 85 варіантів класових здібностей. Невідомих відповідників не виявлено. Це перевірка даних і зіставлення, а не доказ працездатності кожної комбінації в Foundry. Скрипти не відкривають профіль браузера й не змінюють світ.

Адаптер імпорту використовує внутрішні `_DataConverter` установленого Plutonium через його API імпортерів. При несумісності версії він має зупинитися до запису. Після оновлення Plutonium потрібна повторна перевірка `builder.prepare(json)` та імпорту на тестовому аркуші.
